A reliable transport protocol built from scratch on plain UDP sockets, used to answer one question: can a machine-learning model choose the retransmission timeout better than TCP's own formula, RFC 6298?

§1 The problem

UDP delivers nothing reliably. The hard part is knowing when to give up waiting.

UDP gives no guarantee that a datagram arrives, arrives once, or arrives in order. To make it reliable we number every chunk, acknowledge it, and resend it if the acknowledgement does not come back within the retransmission timeout (RTO).

Wait too little and the sender resends packets that were only late. That wastes bandwidth and adds load exactly when the network is struggling.

Wait too long and, after a real loss, the sender sits idle. With a sliding window, one missing packet can stall all new data behind it.

TCP solves this with a formula from 1988 (Jacobson/Karels, standardised as RFC 6298): a smoothed RTT plus four times its variation. This project asks whether a model that has seen thousands of real RTT sequences can set a tighter, smarter timeout.

Why 1,200-byte payloads?

24 header + 1,200 data + 16 optional HMAC + 8 UDP + 20 IPv4 = 1,268 bytes. That is below 1,280, the smallest MTU any IPv6 link may have, so no datagram is ever split by IP. Losing one IP fragment would lose the whole datagram.

    §5 Baseline estimator

    RFC 6298: how TCP decides how long to wait

    Every valid round-trip sample updates a smoothed average and a smoothed deviation. The timeout sits four deviations above the average.

    # first sample R SRTT = R RTTVAR = R / 2 # every later sample R (RTTVAR uses the OLD SRTT) RTTVAR = 3/4 · RTTVAR + 1/4 · |SRTT − R| SRTT = 7/8 · SRTT + 1/8 · R RTO = SRTT + max(G, 4 · RTTVAR) # clamped to [30 ms, 10 s]; 1 s before any sample

    The RFC's 1-second minimum is lowered to 30 ms here. On our 20–300 ms simulated paths a 1 s floor would make every estimator output 1 s and hide every difference.

    Karn's algorithm

    Never time a resent packet

    If a packet was sent twice, its ACK could belong to either copy, so the RTT is ambiguous. Our window only produces a sample when retx == 0.

    Exponential backoff

    Double once per round

    With 64 timers, one outage fires dozens at once. A backoff "epoch" makes the timeout double once per round of timeouts, not once per packet. A valid sample resets it.

    Bug found in testing

    Runaway timeouts

    The first version let old packets push the backoff up again after it had reset. On the lossy network a 50 ms path got a 1.9 s timeout and a 3 MB transfer took 22 s. With epochs it takes 4.3 s.

    §6 ML estimator

    Predict the 95th percentile of the next half-second of RTTs

    A timeout is a threshold, so the model does not predict the average RTT. It predicts a value that about 95 % of upcoming packets will beat, which sets an explicit budget for early timeouts.

    What the model relies on

    impurity-based feature importance

    The RTT level (log_srtt) and the fastest recent RTT (min_rel) dominate. The RTT trend (slope) is almost unused, which explains the failure on the changing network in §8.

    Leakage control

    • Data is split by whole runs (seeds), never by rows: train 0–19, validation 100–105, test 200–205, experiments 1000+.
    • Features use only what the sender has already seen. Simulator settings and the profile name are never inputs.
    • One feature function is shared by training and runtime, and the model file lists the features it expects.

    §7 Method

    Both estimators face exactly the same network

    A comparison is only fair if luck is equal. The proxy decides the fate of each packet copy from a hash of (seed, direction, type, sequence, copy number), not from a shared random stream.

    With a shared random stream, one extra retransmission in one run would shift every later random draw, and the two runs would see different networks. With hashing, "the 2nd copy of chunk 117 is dropped" is true in both runs.

    Each network × seed pair runs once per strategy: RFC 6298 (K = 4), the ML estimator, and an extra control arm, RFC with K = 2, a deliberately shorter timeout. The order of the strategies rotates between seeds.

    Differences are tested per network with an exact Wilcoxon signed-rank test on the 10 paired differences. With 10 pairs the smallest possible p-value is 0.002.

    §8 Results

    210 transfers, all verified. What changed?

    7 networks × 10 seeds × 3 strategies, 1 MiB each. Every received file matched the original byte for byte.

    +6–11 %Faster on jittery and lossy paths

    Goodput rose on lossy, jitter-heavy and duplicate/reorder networks (p = 0.002 each), because lost packets were repaired 9–21 % sooner.

    ≈2×But more wasted resends

    Unnecessary retransmissions roughly doubled. Most of the speed-up is also available from simply shortening the RFC formula (K = 2). Against that, ML wastes 60 % fewer resends under heavy jitter.

    3.8×Worse on a changing path

    When the delay ramps from 15 to 120 ms, the model's timeout lagged behind: no throughput gain and 3.8× the unnecessary resends.

    §9 The main lesson

    More accurate offline did not mean better online

    On held-out test runs the ML timeout was closer to its target and less likely to fire early than RFC 6298. In live transfers it fired early more often. The prediction error alone did not predict protocol behaviour.

    Offline: held-out test runs

    NetworkRFC MAEML MAERFC earlyML early

    MAE = mean |timeout − target| in ms. "Early" = share of upcoming delivered packets whose RTT exceeds the timeout.

    Unseen conditions: leave one network out

    A model trained without the "changing" network was less accurate on it than the plain formula. Tree models do not extrapolate.

    Why offline and online disagree

    • Correlated errors. When a slow period starts, every in-flight timer fires together; one short timeout becomes dozens of resends.
    • Feedback. Each early timeout makes a packet ambiguous under Karn's rule, so history thins out exactly when conditions change.
    • Backoff hides the formula's errors. After a timeout, the doubled RFC value persists and protects it.
    • Covariate shift. Training traces came from the RFC estimator; under ML control the sender sees more resends than any training run.
    §10 Engineering quality

    Tested, defensive, reproducible

    Correctness

    120 automated tests

    • 5,000 random datagrams and every single-bit flip rejected
    • RTO values checked against hand calculations
    • Transfers under every network profile
    • Empty, 1-byte, 8 MiB and binary files
    • Receiver crash, idle sender, hash mismatch
    Security

    Input is hostile until checked

    • One validation boundary for every datagram
    • Filenames with /, .. or control characters rejected
    • Bounded buffers, reads, file size and transfer count
    • Optional HMAC-SHA256 with a pre-shared key
    • No pickle anywhere
    Reproducibility

    Every number is regenerated

    • Seeds recorded in every output file
    • Received files re-hashed independently by the test harness
    • Plots and tables built only from result files
    • Runtime needs only the Python standard library
    Second bug caught by the independent check

    While running experiments, the harness reported files that did not match even though the receiver said "OK". A finished transfer was still reserving its filename, so the next file went to name (1).bin. Fixed, and a regression test now guards it.

    §11 Conclusion

    A useful refinement, safe only with a fallback

    The reliability layer works. 210 out of 210 transfers arrived intact across loss, bursts, jitter, duplication, reordering and corruption.

    The ML timeout is not better in general. It is faster on lossy and jittery paths but wastes more traffic, and most of its speed comes from being shorter. Its real advantage is selectivity under heavy-tailed jitter and burst loss. On a changing path it is worse.

    Limits. One machine over loopback; user-space delay with no queueing or congestion control; trained and tested on the same simulator; 10 seeds per network.

    Next steps. Calibrate on end-to-end waste, retrain on traces collected under ML control, use an asymmetric loss, test over real links with tc netem, and add fast retransmit.
